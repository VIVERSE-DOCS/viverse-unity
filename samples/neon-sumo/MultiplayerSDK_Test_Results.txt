SDK INTEGRATION ISSUES (BUILD / GAME)
================================================================================

1. WebGL/Viverse: game readiness events (OnWaitForPlayer/OnPlayerAllReady/OnMasterNotify) were not forwarded in the JS bridge, and not routed in ReceiveMessageFromJS. Result: WebGL builds can stall at "Waiting for players" even when both clients click Ready. Added bridge + C# routing to align WebGL with Editor behavior.
2. WebGL/Viverse: onMasterNotify fires with valid master_user, but MultiplayerClient.IsMasterUser() returns false. Result: no master-driven actions (spawn, game start, ramp sync). Workaround needed to trust master_user == PeerId in game logic.

================================================================================
GAME MODULE – COUNTDOWN TIMER (KNOWN BEHAVIOR)
================================================================================

The game timer is driven by the backend. The client sends a start signal and receives
countdown ticks. There is a backend warm-up delay between send and first receive.

Event we send:
  - Game.TriggerGameStart() → sends countdown_to_start to backend
  - Payload: { type: "game", event: "countdown_to_start", user_id: "..." }
  - When: At intro start (when spawning/ready flow triggers game start)

Event we receive:
  - OnCountdownToEnd → game/onCountdownToEnd from backend
  - Payload: { second: 60 }, then 59, 58, 57... every second
  - Handler: HandleCountdownToEnd → uiManager.ShowEndCountdown(seconds)

Delay (measured):
  - ~5–6 seconds (Editor/Windows): First countdown_to_end arrives 5–6 seconds after
    countdown_to_start is sent.
  - ~8–9 seconds (WebGL/Viverse): Can be longer in WebGL builds.

Workaround: Send countdown_to_start at intro start (e.g. when spawn ACKs are ready)
so backend warm-up overlaps with 3-2-1-Go. First tick then arrives around or shortly
after "Go!".
